This is Proof Before Pay, an evidence-driven pre-payment exception investigator for small businesses. This walkthrough is aimed at an engineering leader: it will show the product problem, the architecture, the important code decisions, the evidence behind the claims, and the boundaries that keep the system from becoming unsafe automation.

The business problem is not that invoices are hard to read. The problem is that payment evidence is distributed across records that can disagree. An invoice can have the right vendor name and still contain a duplicate invoice number, a price higher than the purchase order, a quantity greater than the goods receipt, or a bank account that was never approved. A fluent summary is not enough when the consequence is money leaving the business.

The product response is deliberately narrow. Proof Before Pay receives supplier evidence, links the relevant records, checks contradictions, and returns PAY, HOLD, or INVESTIGATE for a human reviewer. It does not execute payment, change bank details, or make a definitive fraud declaration. That narrow boundary is a strength: it makes the system reviewable and keeps the high-consequence action outside the model.

The public repository is visible here. The README explains the safety boundaries, the benchmark contract, the runtime prerequisites, the verification commands, and the evidence locations. The repository is structured as an executable project, not only as a prompt or a slide deck: source code, tests, schemas, Docker targets, public cases, traces, and verification scripts live together.

The first architectural decision is a separation of responsibilities. The language model reads messy evidence and produces structured facts. Deterministic tools perform arithmetic and equality checks. A rule evaluator turns anomalies into a recommendation. A schema validator checks the output contract. A human reviewer remains the final authority. This prevents a persuasive model explanation from silently replacing a calculation or a policy decision.

The request path starts in the reviewer UI. A reviewer can upload PDF, image, or JSON evidence, or select a public example. The browser sends an investigation request to the local API. The API normalizes the case, applies request limits, and passes the evidence into the orchestrator. This is a real workflow, but the demo recording uses bounded local fixtures so no personal documents or provider credentials appear in the video.

Now look at the orchestrator. Its control flow is intentionally readable: extract, verify, apply rules, explain, validate, and escalate. Each phase writes a trace event. That means an answer is not just a final label; a reviewer can inspect what happened before the label was returned.

The extraction module contains an important engineering lesson. LLM response schemas are not always strong enough to enforce every required field. The project therefore validates the extracted contract after the model responds. If item quantity, unit price, line total, or invoice totals are missing, it reinforces the prompt, retries once, and applies deterministic repair where the purchase order provides enough evidence. The model is useful, but the contract is enforced outside the model.

The deterministic verification layer checks the things that should not be guessed: invoice math, subtotal and tax, purchase-order prices, received quantities, vendor identity, bank changes, duplicate billing, currency, tax rate, and duplicate line IDs. Decimal calculations and equality helpers make the comparison explicit. The output carries calculation references so the reviewer knows which checks contributed to the decision.

The recommendation policy is conservative. HOLD takes precedence over INVESTIGATE, and INVESTIGATE takes precedence over PAY. A missing document or contradiction should not be converted into confidence just because the language model sounds certain. The system also records skipped checks when evidence is absent, so a reviewer can distinguish verified from unverified.

The reviewer UI is designed around explainability. The result shows the recommendation, the next human action, extracted vendor and invoice facts, linked evidence, automated checks, and an audit trace. This is different from a generic chat answer: the user can move from a decision back to the evidence and then to the exact system phase that produced it.

The API has practical hardening. Investigation POSTs require an X-Auth-Token, the comparison is constant-time, same-origin CORS is the default, and request bodies have a configurable twenty-megabyte cap. The UI injects an ephemeral token for the local same-origin session when no fixed token is configured. These controls do not make the service a complete production platform, but they close obvious abuse paths in the reviewer surface.

The runtime boundary is enforced in Docker. The runtime target receives application code, public contracts, public cases, and the security scanner. The verifier target receives tests, evaluation logic, manifests, and hidden ground truth. The runtime also uses a non-root user and a pinned Python base image. This is important for an evidence-driven benchmark: the agent should not be able to read the answer key it is being judged against.

The repository treats tests as executable evidence. Unit and integration tests cover calculations, extraction, credentials, UI behavior, recovery UX, schemas, manifests, and the orchestrator. The latest host validation recorded 181 passing tests and 2 container-only skips in the project status at the time of the production-hardening work. The full Docker verification path also checks runtime inputs, non-root execution, isolation, and forced-failure behavior.

The benchmark claims need to be read precisely. The accepted Phase 2 run reports 100 percent accuracy and zero unsafe PAY recommendations on twelve synthetic cases. That is a result for that frozen benchmark, not a production generalization claim. Track B measured the pre-fix agent at 75 percent versus an 83.33 percent fair baseline; the extraction fix improved known live cases, but a fresh Track B remeasurement was still pending because the provider quota was exhausted. This is the kind of limitation a senior reviewer should want stated plainly.

The production hardening work also addresses real failure modes. OCR model fallback handles unavailable model names and quota behavior. Missing-document guards distinguish absent evidence from a model dropping an object. Credential cooldown tests freeze time to avoid race conditions. The UI regression suite verifies unauthorized requests, oversized payloads, same-origin token behavior, and ephemeral-port isolation.

The project is different from a generic generative AI tool in three ways. First, it compares a bounded set of business records instead of answering an open-ended question. Second, it delegates arithmetic and equality to deterministic tools. Third, it stops at a human decision boundary and preserves traceable evidence. The value is not that the model writes a clever paragraph; the value is that the workflow makes disagreement visible before payment.

There are still honest operational gaps before broad public production deployment: TLS and ingress ownership, readiness probes, metrics, centralized logs, alerting, secret rotation, rollback procedures, and an operations runbook. Those are not hidden by the demo. The core workflow is executable and tested; the surrounding service operations still need to be formalized for a real deployment environment.

The final takeaway is the engineering posture. Proof Before Pay uses AI where interpretation helps, deterministic code where correctness matters, schemas where contracts matter, traces where accountability matters, and a human where consequences matter. The repository, the tests, the UI, and the container boundary all reinforce the same principle: proof before payment.
